# ♻️ Lifecycle Management

## 🤔 Wat is Lifecycle Management?

Lifecycle Management is een **geautomatiseerd beleid** dat blobs automatisch naar goedkopere tiers verplaatst of verwijdert op basis van **regels** die je instelt.

**Voordelen:**
```
✅ Automatische cost optimization
✅ Geen manual tier management
✅ Rule-based transitions
✅ Scheduled deletions
✅ Runs daily
```

---

## 📋 Requirements

```
Storage Account Type:
✅ General Purpose v2
❌ General Purpose v1
❌ BlobStorage (legacy)

Blob Containers:
✅ Regular containers
❌ $logs container
❌ $web container (static websites)
```

## 🎯 Lifecycle Actions

### Vijf Hoofdacties

| Action | Beschrijving | Applies To |
|--------|--------------|------------|
| **tierToCool** | Verplaats naar Cool tier | Block, Append blobs |
| **tierToCold** | Verplaats naar Cold tier | Block blobs |
| **tierToArchive** | Verplaats naar Archive tier | Block blobs |
| **delete** | Verwijder blob | All blob types |
| **enableAutoTierToHotFromCool** | Auto promote van Cool naar Hot | Block blobs |

### Action Scope

Policies kunnen toepassen op:
```
1. Base Blob (current version)
2. Snapshots
3. Versions (blob versioning)
```

## 📝 Policy Structure

### JSON Format

```json
{
  "rules": [
    {
      "enabled": true,
      "name": "rulename",
      "type": "Lifecycle",
      "definition": {
        "actions": {
          "baseBlob": {
            "tierToCool": {
              "daysAfterModificationGreaterThan": 30
            },
            "tierToArchive": {
              "daysAfterModificationGreaterThan": 90,
              "daysAfterLastTierChangeGreaterThan": 7
            },
            "delete": {
              "daysAfterModificationGreaterThan": 365
            }
          },
          "snapshot": {
            "delete": {
              "daysAfterCreationGreaterThan": 90
            }
          },
          "version": {
            "delete": {
              "daysAfterCreationGreaterThan": 90
            }
          }
        },
        "filters": {
          "blobTypes": ["blockBlob"],
          "prefixMatch": ["container1/folder1/"],
          "blobIndexMatch": [
            {"name": "Environment", "op": "==", "value": "Production"}
          ]
        }
      }
    }
  ]
}
```

## ⏰ Condition Types

### 1. daysAfterModificationGreaterThan

**Gebruik:** Gebaseerd op last modified time

```json
"tierToCool": {
  "daysAfterModificationGreaterThan": 30
}
```

**Wanneer triggers:**
```
Blob last modified: 2024-01-01
Check date: 2024-02-05
Days passed: 35
Trigger: ✅ (35 > 30)
```

**Toepasbaar op:** baseBlob

### 2. daysAfterCreationGreaterThan

**Gebruik:** Gebaseerd op creation time

```json
"delete": {
  "daysAfterCreationGreaterThan": 90
}
```

**Wanneer triggers:**
```
Blob created: 2024-01-01
Check date: 2024-04-05
Days passed: 94
Trigger: ✅ (94 > 90)
```

**Toepasbaar op:** snapshot, version

### 3. daysAfterLastAccessTimeGreaterThan

**Gebruik:** Gebaseerd op last access time

**⚠️ Requires:** Access tracking enabled!

```bash
# Enable access tracking
az storage account blob-service-properties update \
  --account-name mystorageaccount \
  --enable-last-access-tracking true
```

```json
"tierToCool": {
  "daysAfterLastAccessTimeGreaterThan": 60
}
```

**Tracking behavior:**
```
First read in 24 hours: Tracked ✅
Additional reads: Not tracked (within 24h)
Cost: Small additional cost for tracking
```

**Wanneer triggers:**
```
Blob last accessed: 2024-01-01
Check date: 2024-03-15
Days passed: 74
Trigger: ✅ (74 > 60)
```

### 4. daysAfterLastTierChangeGreaterThan

**Gebruik:** Voor Archive tier (avoid thrashing)

```json
"tierToArchive": {
  "daysAfterModificationGreaterThan": 90,
  "daysAfterLastTierChangeGreaterThan": 7
}
```

**Voorkomt:**
```
Day 0:  Blob created (Hot)
Day 30: Policy moves to Cool
Day 31: Another policy tries Archive
        → Blocked! (7 days since tier change)
Day 37: Now eligible for Archive ✅
```

## 🎯 Filters

### 1. blobTypes

**Restricts actions to specific blob types:**

```json
"filters": {
  "blobTypes": ["blockBlob"]
}
```

**Options:**
- `"blockBlob"` - Block blobs
- `"appendBlob"` - Append blobs (limited actions)

**Note:** Page blobs niet ondersteund in lifecycle policies

### 2. prefixMatch

**Restricts to specific containers/folders:**

```json
"filters": {
  "prefixMatch": [
    "container1/",
    "container2/logs/"
  ]
}
```

**Matching rules:**
```
Exact match (with trailing /):
"container1/" → Matches: container1/blob1
             → Matches: container1/folder/blob2

Wildcard (without trailing /):
"container1" → Matches: container1/blob1
            → Matches: container1-backup/blob2

Multiple prefixes:
["logs/", "archives/"] → OR condition
```

### 3. blobIndexMatch

**Restricts based on blob index tags:**

```json
"filters": {
  "blobIndexMatch": [
    {"name": "Environment", "op": "==", "value": "Production"},
    {"name": "Status", "op": "==", "value": "Processed"}
  ]
}
```

**Tag format:**
```
Up to 10 tag conditions per rule
AND condition (all must match)
```

**Set tags via CLI:**
```bash
az storage blob tag set \
  --container-name mycontainer \
  --name myblob.txt \
  --tags Environment=Production Status=Processed
```

Blob not accessed for 30 days in Hot → Stays Hot

## ⏰ Execution Timing

### Daily Execution

```
Policy runs: Once per day
Execution time: Not guaranteed specific time
Processing: Can take up to 24 hours
First run: Up to 24 hours after creation
```

**Timeline example:**
```
Day 0, 10:00: Create policy
Day 1, 08:00: Policy first execution ✅
Day 1, 08:00-Day 2, 08:00: Actions processed
Day 2, 08:00: Policy second execution ✅
```

### Action Precedence

**Least expensive action wins:**

```
Multiple actions on same blob:
├── delete (hoogste prioriteit)
├── tierToArchive
├── tierToCold
└── tierToCool (laagste prioriteit)

Example:
Rule 1: tierToCool at 30 days
Rule 2: delete at 30 days
Result: Blob deleted ✅ (cheaper)
```

## ⚠️ Important Considerations

### 1. Set Blob Tier Interaction

```
Manual tier change via Set Blob Tier:
└── Updates last tier change time
    └── May affect lifecycle policy!
    
Example:
Day 0:   Create blob (Hot)
Day 30:  Policy → Cool
Day 31:  Manual → Hot (via Set Blob Tier)
Day 60:  Policy tries Archive
         → Blocked! (daysAfterLastTierChangeGreaterThan)
```

**⚠️ Risk:**
```
Lifecycle policy checks last modified time
Set Blob Tier does NOT update last modified
→ Policy might revert your manual change!

Solution:
├── Disable policy temporarily, OR
└── Use blob index tags to exclude
```

### 2. Partial Updates Not Supported

```
❌ Cannot update single rule
✅ Must upload complete policy JSON
```

**Workflow:**
```
1. Download existing policy
2. Modify JSON
3. Upload complete policy
```

### 3. No Archive Tier Support for Premium

```
Premium Block Blob Storage:
❌ Cannot use tierToArchive
❌ Cannot use tierToCool
✅ Can use delete
```

### 4. Cost Implications

```
Early deletion penalties still apply:
├── Cool: 30 days minimum
├── Cold: 90 days minimum
└── Archive: 180 days minimum

Example:
Day 0:  Create → Hot
Day 20: Policy → Cool
Day 30: Policy → Delete
Charge: 30 days Cool (10 days penalty!)
```

## ✅ Best Practices

### 1. Test Policies First

```
Before production:
1. Create test storage account
2. Upload sample data
3. Create policy with short timeframes
4. Monitor for 2-3 days
5. Verify expected behavior
```

### 2. Use Blob Index Tags

```
Tag-based filtering:
✅ More flexible than prefixes
✅ Can change without moving blobs
✅ Supports complex scenarios

Example:
Tag: Retention=Short → Delete after 30 days
Tag: Retention=Long → Delete after 365 days
```

### 3. Monitor Execution

```
Azure Monitor metrics:
├── BlobCapacity (per tier)
├── Transactions
└── Ingress/Egress

Check regularly:
└── Ensure policy behaves as expected
```

### 4. Document Your Policies

```
Add comments in JSON (not parsed):
{
  "_comment": "Images older than 6 months archived",
  "rules": [ ... ]
}
```

### 5. Gradual Tier Transitions

```
✅ Good:
Hot → Cool (30d) → Cold (90d) → Archive (180d)

❌ Avoid:
Hot → Archive (90d)
└── Might need data in Cool period!
```

### 6. Consider Access Patterns

```
Analyze before creating policy:
├── How often is data accessed?
├── What is data lifecycle?
├── Are there compliance requirements?
└── What are cost implications?

Tools:
└── Azure Storage Analytics
└── Access logs
```

## 🎓 Samenvatting

### Key Takeaways

1. **Lifecycle Management** = Automated cost optimization
2. **Runs daily** - Actions can take up to 24 hours
3. **Rule-based** - Filters on type, prefix, tags
4. **Conditions** - After modification, creation, access, tier change
5. **Actions** - Tier transitions and deletions
6. **Precedence** - Cheapest action wins
7. **No partial updates** - Always upload complete policy

### Quick Decision Guide

```
Use Lifecycle Management when:
├── Predictable data aging patterns
├── Large data volumes
├── Manual management not feasible
└── Cost optimization is priority

Avoid when:
├── Unpredictable access patterns
├── Small data volumes
├── Frequent manual interventions needed
└── Complex business logic required
```

### Common Patterns

```
Logs:
Hot (7d) → Cool (30d) → Delete (90d)

Backups:
Hot (7d) → Cool (30d) → Archive (180d) → Delete (730d)

Media:
Hot (30d) → Cool (90d) → Archive (365d)

Documents:
Hot (90d) → Cool (180d) → Cold (365d) → Archive (1825d)
```
