# 💰 Azure Cosmos DB - Request Units & Throughput

## 📖 Wat zijn Request Units (RUs)?

**Request Units (RUs)** zijn de **valuta** van Azure Cosmos DB. Elke database operatie (read, write, query) kost een bepaald aantal RUs. Het is een **geabstraheerde maat** voor de resources (CPU, geheugen, IOPS) die nodig zijn voor een operatie.

### 🎯 Waarom Request Units?

| Voordeel | Beschrijving |
|----------|--------------|
| **🔄 Voorspelbaar** | Consistent pricing model ongeacht workload |
| **📊 Transparant** | Elke operatie toont hoeveel RUs het kost |
| **⚡ Performance garantie** | Provisioned RUs zorgen voor consistent performance |
| **💰 Cost management** | Betaal alleen voor wat je provisioned hebt |

---

## 📏 RU Kosten - Baseline

De kosten van een operatie worden beïnvloed door verschillende factoren:

### 🔢 Baseline Voorbeeld

```
Point Read (ReadItemAsync):
├─ 1 KB item → 1 RU
├─ 10 KB item → ~10 RU
└─ 100 KB item → ~100 RU

Write (CreateItemAsync):
├─ 1 KB item → ~5 RU
├─ 10 KB item → ~50 RU
└─ 100 KB item → ~500 RU
```

**📌 Vuistregel:**  
- **Point read (met id + partition key):** ~1 RU per KB
- **Write:** ~5 RU per KB
- **Query:** Variabel (afhankelijk van complexity en result set size)

---

## 🎚️ Factoren die RU Kosten Beïnvloeden

| Factor | Impact | Details |
|--------|--------|---------|
| **📦 Item size** | 🔴 Hoog | Grotere items = meer RUs |
| **🔍 Query complexity** | 🔴 Hoog | JOINs, aggregations, functions verhogen RU cost |
| **📑 Indexing** | 🟡 Matig | Indexed properties = snellere queries maar hogere write costs |
| **🎚️ Consistency level** | 🟡 Matig | Strong consistency = hogere RU cost |
| **🔢 Result set size** | 🔴 Hoog | Meer returned items = meer RUs |
| **🔀 Cross-partition** | 🔴 Hoog | Queries over meerdere partitions zijn duurder |

## 💻 RU Kosten Meten

```csharp
using Microsoft.Azure.Cosmos;

var container = cosmosClient.GetContainer("database", "container");

// ========================================
// Point Read RU Cost
// ========================================
ItemResponse<User> readResponse = await container.ReadItemAsync<User>(
    id: "user-123",
    partitionKey: new PartitionKey("user-123")
);
Console.WriteLine($"Point read RU: {readResponse.RequestCharge}"); // ~1 RU voor 1KB

// ========================================
// Write RU Cost
// ========================================
var newUser = new User { id = "user-456", name = "John" };
ItemResponse<User> createResponse = await container.CreateItemAsync(newUser);
Console.WriteLine($"Create RU: {createResponse.RequestCharge}"); // ~5 RU voor 1KB

// ========================================
// Query RU Cost
// ========================================
var query = new QueryDefinition("SELECT * FROM c WHERE c.age > 25");
FeedIterator<User> iterator = container.GetItemQueryIterator<User>(query);

double totalRU = 0;
while (iterator.HasMoreResults)
{
    FeedResponse<User> response = await iterator.ReadNextAsync();
    totalRU += response.RequestCharge;
    Console.WriteLine($"Page RU: {response.RequestCharge}");
}
Console.WriteLine($"Total query RU: {totalRU}"); // Kan variëren van 2 RU tot 1000+ RU

// ========================================
// Single-partition vs Cross-partition Query
// ========================================

// Single-partition query (goedkoop)
var singleQuery = new QueryDefinition("SELECT * FROM c WHERE c.userId = @id")
    .WithParameter("@id", "user-123");
    
FeedIterator<User> singleIterator = container.GetItemQueryIterator<User>(
    singleQuery,
    requestOptions: new QueryRequestOptions { PartitionKey = new PartitionKey("user-123") }
);
// RU cost: 2-10 RU (afhankelijk van aantal items in partition)

// Cross-partition query (duur)
var crossQuery = new QueryDefinition("SELECT * FROM c WHERE c.age > 25");
FeedIterator<User> crossIterator = container.GetItemQueryIterator<User>(crossQuery);
// RU cost: 50-500+ RU (scant meerdere partitions)
```

## 🏗️ Throughput Modes

Azure Cosmos DB biedt **drie throughput modes** om aan verschillende workload requirements te voldoen:

```
┌────────────────────────────────────────────┐
│        Throughput Mode Keuze               │
├────────────────────────────────────────────┤
│ 1. Provisioned (Manual)     🧊 Predictable│
│ 2. Autoscale               ⚡ Dynamic      │
│ 3. Serverless              💸 Pay-per-use │
└────────────────────────────────────────────┘
```

---

## 🧊 1. Provisioned Throughput (Manual)

**💡 Omschrijving:**  
Je **reserveert** een vast aantal RU/s (Request Units per seconde). Je betaalt voor deze gereserveerde capaciteit, ongeacht of je het gebruikt.

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Minimum** | **400 RU/s** per container/database |
| **Granulariteit** | Instelbaar in stappen van **100 RU/s** |
| **Billing** | Betaal per uur voor **provisioned** RU/s |
| **Performance** | **Consistent** en **voorspelbaar** |
| **SLA** | ✅ Volledige **SLA garantie** voor throughput |

### 🎯 Twee Sub-modes

#### A. Container-level (Dedicated Throughput)

**Wat:** Elke container krijgt **dedicated** RU/s die **niet worden gedeeld**.

```
Container A: 1000 RU/s ← Dedicated
Container B: 2000 RU/s ← Dedicated
Container C: 500 RU/s  ← Dedicated
Total: 3500 RU/s
```

**✅ Voordelen:**
- **Gegarandeerde performance** per container
- Geen resource contention tussen containers
- Ideaal voor mission-critical containers

**❌ Nadelen:**
- Duurder (betaal voor elke container apart)
- Kan underutilized zijn als traffic varieert

**🎯 Use Cases:**
- High-throughput containers (> 1000 RU/s)
- Production workloads met strikte performance requirements
- Containers met voorspelbare, consistente load

---

#### B. Database-level (Shared Throughput)

**Wat:** Meerdere containers **delen** de RU/s van de database.

```
Database: 4000 RU/s (shared)
├─ Container A: ~1500 RU/s (dynamic)
├─ Container B: ~1000 RU/s (dynamic)
├─ Container C: ~500 RU/s  (dynamic)
└─ Container D: ~1000 RU/s (dynamic)

Note: Containers met dedicated throughput nemen NIET deel aan sharing
```

**✅ Voordelen:**
- **Kostenefficiënt** (één pool van RUs)
- Flexibel voor containers met lage traffic
- Goede utilization bij fluctuerende workloads

**❌ Nadelen:**
- Containers kunnen elkaar beïnvloeden
- Geen performance garantie per container
- Minimum: **400 RU/s** voor database (ongeacht aantal containers)

**🎯 Use Cases:**
- Development/testing environments
- Multi-container apps met lage tot matige load
- Cost-sensitive workloads
- Containers met complementary usage patterns

---

### 💻 Provisioned Throughput - Code

```bash
# ========================================
# Azure CLI
# ========================================

# Container-level (Dedicated) throughput
az cosmosdb sql container create \
  --account-name mycosmosaccount \
  --database-name mydatabase \
  --name mycontainer \
  --partition-key-path "/userId" \
  --throughput 1000

# Database-level (Shared) throughput
az cosmosdb sql database create \
  --account-name mycosmosaccount \
  --name mydatabase \
  --throughput 4000

# Container binnen shared database (neemt deel aan sharing)
az cosmosdb sql container create \
  --account-name mycosmosaccount \
  --database-name mydatabase \
  --name sharedcontainer \
  --partition-key-path "/userId"
  # Geen --throughput → gebruikt database-level throughput

# Update throughput (scale up/down)
az cosmosdb sql container throughput update \
  --account-name mycosmosaccount \
  --database-name mydatabase \
  --name mycontainer \
  --throughput 2000
```

```csharp
// ========================================
// C# SDK
// ========================================

// Container met dedicated throughput
Container container = await database.CreateContainerIfNotExistsAsync(
    id: "users",
    partitionKeyPath: "/userId",
    throughput: 1000 // Dedicated 1000 RU/s
);

// Database met shared throughput
Database database = await cosmosClient.CreateDatabaseIfNotExistsAsync(
    id: "mydatabase",
    throughput: 4000 // Shared 4000 RU/s
);

// Container zonder throughput (gebruikt database sharing)
Container sharedContainer = await database.CreateContainerIfNotExistsAsync(
    id: "sharedcontainer",
    partitionKeyPath: "/userId"
    // Geen throughput parameter → shared
);

// Throughput updaten (scale up/down)
await container.ReplaceThroughputAsync(2000);

// Throughput ophalen
int? currentThroughput = await container.ReadThroughputAsync();
Console.WriteLine($"Current throughput: {currentThroughput} RU/s");
```

## ⚡ 2. Autoscale Throughput

**💡 Omschrijving:**  
Cosmos DB **schaalt automatisch** tussen **10% en 100%** van een ingestelde **maximum** RU/s, gebaseerd op de daadwerkelijke workload.

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Minimum** | **100 RU/s** (10% van 1000 RU/s max) |
| **Maximum** | Door jou ingesteld (bijv. 4000 RU/s) |
| **Auto-scaling range** | 10% - 100% van maximum |
| **Billing** | Betaal per **hoogste RU/s bereikt in dat uur** |
| **SLA** | ✅ Volledige **SLA garantie** |

### 🔄 Hoe Werkt Autoscale?

```
Autoscale max: 4000 RU/s

Scaling range:
├─ Minimum: 400 RU/s  (10% van 4000)
├─ Midpoint: 2000 RU/s (50% van 4000)
└─ Maximum: 4000 RU/s (100% van 4000)

Timeline:
09:00 - Low traffic  → 500 RU/s  (betaal voor 500)
10:00 - Medium       → 1500 RU/s (betaal voor 1500)
11:00 - Peak traffic → 3800 RU/s (betaal voor 3800)
12:00 - Medium       → 1200 RU/s (betaal voor 1200)
```

**💰 Kosten:**  
Je betaalt voor de **hoogste RU/s** die **in dat uur** is bereikt. Dit is ongeveer **1.5x** duurder dan manual provisioned voor hetzelfde maximum.

### ✅ Voordelen vs ❌ Nadelen

| ✅ Voordelen | ❌ Nadelen |
|--------------|------------|
| Automatische schaling | ~1.5x duurder dan manual bij constante max load |
| Ideaal voor **onvoorspelbare** workloads | Minimum is 10% van max (kan te hoog zijn) |
| Voorkomt **throttling** bij spikes | Scaling heeft enkele seconden vertraging |
| SLA garantie behouden | Niet beschikbaar voor serverless |

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **Unpredictable traffic patterns** (dagelijkse/wekelijkse pieken)
- **New applications** (onbekende load)
- **Seasonal workloads** (retail tijdens feestdagen)
- **Development databases** (variabele testing loads)

❌ **Wanneer niet te gebruiken:**
- **Constant high traffic** (manual provisioned is goedkoper)
- **Ultra low traffic** (serverless is goedkoper)
- **Zeer strikte cost control** (billing is minder voorspelbaar)

---

### 💻 Autoscale - Code

```bash
# ========================================
# Azure CLI
# ========================================

# Container met autoscale
az cosmosdb sql container create \
  --account-name mycosmosaccount \
  --database-name mydatabase \
  --name mycontainer \
  --partition-key-path "/userId" \
  --throughput-type autoscale \
  --max-throughput 4000

# Database met autoscale (shared)
az cosmosdb sql database create \
  --account-name mycosmosaccount \
  --name mydatabase \
  --throughput-type autoscale \
  --max-throughput 4000

# Update autoscale maximum
az cosmosdb sql container throughput update \
  --account-name mycosmosaccount \
  --database-name mydatabase \
  --name mycontainer \
  --throughput-type autoscale \
  --max-throughput 10000
```

```csharp
// ========================================
// C# SDK
// ========================================

// Container met autoscale
Container container = await database.CreateContainerIfNotExistsAsync(
    containerProperties: new ContainerProperties
    {
        Id = "users",
        PartitionKeyPath = "/userId"
    },
    throughputProperties: ThroughputProperties.CreateAutoscaleThroughput(4000) // Max 4000 RU/s
);

// Database met autoscale (shared)
Database database = await cosmosClient.CreateDatabaseIfNotExistsAsync(
    id: "mydatabase",
    throughputProperties: ThroughputProperties.CreateAutoscaleThroughput(4000)
);

// Check autoscale settings
ThroughputProperties throughput = await container.ReadThroughputAsync();
if (throughput.AutoscaleMaxThroughput.HasValue)
{
    Console.WriteLine($"Autoscale max: {throughput.AutoscaleMaxThroughput} RU/s");
    Console.WriteLine($"Current: {throughput.Throughput} RU/s (actual usage)");
}

// Update autoscale max
await container.ReplaceThroughputAsync(
    ThroughputProperties.CreateAutoscaleThroughput(10000)
);

// Convert van manual naar autoscale
await container.ReplaceThroughputAsync(
    ThroughputProperties.CreateAutoscaleThroughput(4000)
);

// Convert van autoscale naar manual
await container.ReplaceThroughputAsync(
    ThroughputProperties.CreateManualThroughput(1000)
);
```

## 💸 3. Serverless Mode

**💡 Omschrijving:**  
**Geen provisioned throughput** nodig. Je betaalt alleen voor de **daadwerkelijk gebruikte RUs** aan het einde van de billing period.

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Provisioning** | ❌ Geen throughput instellen nodig |
| **Billing** | Betaal per **consumed RU** (pay-per-use) |
| **Maximum** | **5000 RU/s burst** mogelijk |
| **Storage** | Max **50 GB** per container |
| **SLA** | ⚠️ **Geen throughput SLA** (best-effort) |

### 📊 Cost Model

```
Serverless billing:
├─ RU consumption: $0.25 per million RUs (voorbeeld pricing)
├─ Storage: $0.25 per GB/month
└─ Geen vaste kosten

Voorbeeld:
Maand met:
├─ 10 miljoen RUs consumed
├─ 5 GB gemiddelde storage
Total: (10 × $0.25) + (5 × $0.25) = $3.75
```

### ✅ Voordelen vs ❌ Nadelen

| ✅ Voordelen | ❌ Nadelen |
|--------------|------------|
| **Geen upfront kosten** | Geen throughput SLA |
| Ideaal voor **lage** en **onvoorspelbare** traffic | Max 50 GB storage per container |
| **Eenvoudig** (geen throughput management) | Max 5000 RU/s burst |
| **True pay-per-use** | Niet geschikt voor hoge, consistente loads |

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **Development & testing** (lage costs, variabele load)
- **Proof of concepts** (geen lange-termijn commitment)
- **Low-traffic applications** (< 5000 RU/s)
- **Intermittent workloads** (event-driven, scheduled jobs)
- **Startups** (lage initial costs)

❌ **Wanneer niet te gebruiken:**
- **Production workloads** (geen SLA)
- **High-throughput apps** (> 5000 RU/s sustained)
- **Large datasets** (> 50 GB)
- **Mission-critical apps** (geen performance garantie)

---

### 💻 Serverless - Code

```bash
# ========================================
# Azure CLI
# ========================================

# Serverless account aanmaken (account-level setting!)
az cosmosdb create \
  --name myserverlessaccount \
  --resource-group myResourceGroup \
  --capabilities EnableServerless \
  --locations regionName=westeurope

# Database in serverless account
az cosmosdb sql database create \
  --account-name myserverlessaccount \
  --name mydatabase
  # Geen --throughput parameter!

# Container in serverless account
az cosmosdb sql container create \
  --account-name myserverlessaccount \
  --database-name mydatabase \
  --name mycontainer \
  --partition-key-path "/userId"
  # Geen --throughput parameter!
```

```csharp
// ========================================
// C# SDK
// ========================================

// Connect naar serverless account (geen verschil in connection)
var cosmosClient = new CosmosClient("<serverless-account-endpoint>", "<key>");

// Database aanmaken (geen throughput parameter)
Database database = await cosmosClient.CreateDatabaseIfNotExistsAsync("mydatabase");

// Container aanmaken (geen throughput parameter)
Container container = await database.CreateContainerIfNotExistsAsync(
    id: "users",
    partitionKeyPath: "/userId"
    // Geen throughput → serverless
);

// Operations zijn identiek
ItemResponse<User> response = await container.CreateItemAsync(user);
Console.WriteLine($"RU consumed: {response.RequestCharge}"); // Billing gebaseerd op dit getal

// ⚠️ Let op: ReadThroughputAsync werkt NIET in serverless
try
{
    int? throughput = await container.ReadThroughputAsync();
}
catch (CosmosException ex) when (ex.StatusCode == System.Net.HttpStatusCode.BadRequest)
{
    Console.WriteLine("Serverless mode heeft geen throughput concept");
}
```

## 📊 Throughput Mode Vergelijking

| Criterium | Provisioned (Manual) | Autoscale | Serverless |
|-----------|---------------------|-----------|------------|
| **Minimum RU/s** | 400 RU/s | 100 RU/s (10% van max) | N/A (pay-per-use) |
| **Billing** | Per provisioned RU/s | Per max RU/s bereikt in uur | Per consumed RU |
| **SLA** | ✅ Volledig | ✅ Volledig | ❌ Best-effort |
| **Max burst** | Provisioned limiet | Configured max | 5000 RU/s |
| **Max storage** | Onbeperkt | Onbeperkt | 50 GB per container |
| **Best for** | Predictable, high load | Unpredictable load | Low, intermittent load |
| **Cost @ low traffic** | 💰 Hoog (betaal minimum) | 💰 Matig (10% van max) | 💸 Laag (pay-per-use) |
| **Cost @ high traffic** | 💸 Laag (constant rate) | 💰 Matig (1.5x provisioned) | 💰 Hoog (per RU) |

## 🎯 Decision Tree: Welke Throughput Mode?

```
START: Kies Throughput Mode
  │
  ├─❓ Is dit een production workload met SLA requirements?
  │   └─ Nee → Serverless 💸 (development/testing)
  │   └─ Ja ↓
  │
  ├─❓ Is je traffic pattern voorspelbaar en consistent?
  │   └─ Ja → Provisioned (Manual) 🧊 (goedkoopst bij constant load)
  │   └─ Nee ↓
  │
  ├─❓ Heb je significante pieken en dalen in traffic?
  │   └─ Ja → Autoscale ⚡ (voorkomt throttling)
  │   └─ Nee → Provisioned (Manual) 🧊
  │
  └─❓ Binnen Provisioned: Dedicated of Shared?
      ├─ Hoge throughput (>1000 RU/s) per container → Dedicated
      ├─ Mission-critical met performance garantie → Dedicated
      └─ Meerdere low-traffic containers → Shared (kostenefficiënt)
```

## ⚠️ Throttling (429 Errors)

Wanneer je **meer RUs consumeert** dan je provisioned hebt, krijg je **HTTP 429** errors (Rate Limited).

### 🔍 Wat gebeurt er?

```
Provisioned: 400 RU/s

Request komt binnen die 500 RUs kost
→ Cosmos DB REJECTS de request
→ HTTP 429 "Request rate too large"
→ Retry-After header suggereert wachttijd (bijv. 10 ms)
```

### 🛠️ Oplossingen

| Aanpak | Wanneer |
|--------|---------|
| **Scale up throughput** | Traffic groei is permanent |
| **Autoscale enablen** | Traffic is spiky/unpredictable |
| **Optimize queries** | Queries zijn inefficiënt (cross-partition, geen indexes) |
| **Partition key heroverweging** | Hot partition probleem |
| **Retry logic** | Tijdelijke spikes (SDK heeft built-in retry) |

### 💻 Retry Logic (Built-in)

```csharp
// SDK heeft automatische retry voor 429 errors
var clientOptions = new CosmosClientOptions
{
    MaxRetryAttemptsOnRateLimitedRequests = 9, // Default: 9
    MaxRetryWaitTimeOnRateLimitedRequests = TimeSpan.FromSeconds(30) // Default: 30s
};

var cosmosClient = new CosmosClient("<endpoint>", "<key>", clientOptions);

// SDK retried automatisch bij 429 errors
// Als alle retries falen → CosmosException met StatusCode 429
try
{
    await container.CreateItemAsync(item);
}
catch (CosmosException ex) when (ex.StatusCode == System.Net.HttpStatusCode.TooManyRequests)
{
    Console.WriteLine("Throttled na alle retries");
    Console.WriteLine($"Retry after: {ex.RetryAfter}");
}
```

## 📈 Monitoring & Optimization

### Azure Portal Metrics

| Metric | Wat te monitoren |
|--------|------------------|
| **Total Request Units** | Hoeveel RUs worden consumed |
| **Normalized RU Consumption** | Percentage van provisioned RUs (>80% = overweeg scale up) |
| **Throttled Requests (429)** | Aantal rate-limited requests |
| **Request Charge by Operation** | Welke operaties zijn duurste? |

### 💡 Cost Optimization Tips

```csharp
// ========================================
// 1. Gebruik Point Reads
// ========================================
// ✅ Point read: 1 RU
ItemResponse<User> pointRead = await container.ReadItemAsync<User>(
    id: "user-123",
    partitionKey: new PartitionKey("user-123")
);

// ❌ Query: 5-10+ RU
var query = new QueryDefinition("SELECT * FROM c WHERE c.id = @id")
    .WithParameter("@id", "user-123");

// ========================================
// 2. Disable Response Content (writes)
// ========================================
// Als je created/updated item niet nodig hebt
ItemResponse<User> response = await container.CreateItemAsync(
    item: user,
    requestOptions: new ItemRequestOptions
    {
        EnableContentResponseOnWrite = false // Scheelt ~50% RU
    }
);

// ========================================
// 3. Gebruik Projections (SELECT specific fields)
// ========================================
// ❌ Duur: SELECT * (retourneert alle fields)
var expensiveQuery = new QueryDefinition("SELECT * FROM c WHERE c.age > 25");

// ✅ Goedkoop: SELECT alleen benodigde fields
var cheapQuery = new QueryDefinition("SELECT c.id, c.name FROM c WHERE c.age > 25");

// ========================================
// 4. Single-partition Queries
// ========================================
// Altijd partition key meegeven als mogelijk
var query = new QueryDefinition("SELECT * FROM c WHERE c.status = @status")
    .WithParameter("@status", "active");
    
FeedIterator<User> iterator = container.GetItemQueryIterator<User>(
    queryDefinition: query,
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKey("user-123") // Blijft binnen één partition
    }
);

// ========================================
// 5. Exclude Unused Paths from Indexing
// ========================================
var containerProperties = new ContainerProperties
{
    Id = "users",
    PartitionKeyPath = "/userId",
    IndexingPolicy = new IndexingPolicy
    {
        Automatic = true,
        IndexingMode = IndexingMode.Consistent
    }
};

// Exclude large fields die je nooit queried
containerProperties.IndexingPolicy.ExcludedPaths.Add(
    new ExcludedPath { Path = "/largeTextField/*" }
);
containerProperties.IndexingPolicy.ExcludedPaths.Add(
    new ExcludedPath { Path = "/blobData/*" }
);

// Lagere write costs (geen indexing overhead)
```

## 🏆 Best Practices

### ✅ Do's

| Praktijk | Reden |
|----------|-------|
| **Start met Autoscale** | Veilig voor nieuwe workloads |
| **Monitor Normalized RU Consumption** | >80% sustained = time to scale |
| **Use point reads** | 1 RU vs 5-50 RU voor query |
| **Enable retry logic** | Built-in SDK retries werken goed |
| **Right-size throughput** | Overprovisioning verspilt geld |
| **Test query costs** | Meet RU charges in development |

### ❌ Don'ts

| Anti-pattern | Waarom niet? |
|--------------|---------------|
| **Under-provision bij high load** | Leidt tot throttling en poor UX |
| **Over-provision bij low load** | Verspilling van geld |
| **Negeer 429 errors** | Indicates performance problemen |
| **Serverless voor production** | Geen SLA guarantees |
| **Cross-partition queries overal** | Zeer duur (kan 10x-100x meer RUs kosten) |
| **SELECT * in queries** | Verspilt RUs door ongebruikte data |
