# 🔀 Azure Cosmos DB - Partitioning

## 📖 Wat is Partitioning?

**Partitioning** is het **verdelen van data** over meerdere fysieke servers (partitions) om **horizontale schaalbaarheid** te bereiken. Dit is cruciaal voor het bereiken van hoge throughput en lage latency in grote datasets.

### 🎯 Waarom Partitioning?

| Voordeel | Beschrijving |
|----------|--------------|
| **⚡ Performance** | Parallelle verwerking over meerdere partitions |
| **📊 Onbeperkte schaal** | Storage en throughput schalen onafhankelijk |
| **💰 Cost efficiency** | Betaal alleen voor wat je gebruikt |
| **🌍 Global distribution** | Efficiënte data distributie wereldwijd |

---

## 🔑 Partition Key

De **partition key** is de **belangrijkste design beslissing** bij het maken van een Cosmos DB container. Het bepaalt hoe je data wordt verdeeld en heeft directe impact op performance.

### 📋 Belangrijke Eigenschappen

| Eigenschap | Details |
|------------|---------|
| **Format** | Altijd met **`/`** prefix (bijv. `/userId`, `/category`) |
| **Type** | Alleen **string** waarden ondersteund |
| **Immutable** | **Kan NIET worden gewijzigd** na container creatie |
| **Vereist** | **Verplicht** bij elke write/read operatie |
| **Case-sensitive** | `/UserId` ≠ `/userId` |

### 🎨 Partition Key Path

```json
// Container met partition key "/userId"
{
  "id": "12345",
  "userId": "user-abc",  // ← Dit is de partition key property
  "name": "John Doe",
  "email": "john@example.com"
}

// Container met nested partition key "/address/city"
{
  "id": "67890",
  "address": {
    "city": "Amsterdam",  // ← Nested partition key
    "street": "Damrak 1"
  },
  "name": "Jane Doe"
}
```

## 📦 Logical Partitions

Een **logical partition** is een **groep items** die **dezelfde partition key waarde** delen.

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Grouping** | Alle items met dezelfde partition key waarde |
| **Max storage** | **20 GB** per logical partition |
| **Max throughput** | **10,000 RU/s** per logical partition |
| **Transactions** | ACID transacties mogelijk binnen één logical partition |
| **Queries** | Queries binnen één partition zijn goedkoopst |

### 💡 Voorbeeld

```
Container: Orders
Partition Key: /customerId

Logical Partition "customer-123":
├─ Order-001 (customerId: "customer-123", total: €50)
├─ Order-002 (customerId: "customer-123", total: €75)
└─ Order-003 (customerId: "customer-123", total: €120)
Total: 3 items, beperkt tot 20 GB

Logical Partition "customer-456":
├─ Order-004 (customerId: "customer-456", total: €200)
└─ Order-005 (customerId: "customer-456", total: €30)
Total: 2 items, beperkt tot 20 GB
```

### ⚠️ Hot Partitions

Een **hot partition** ontstaat wanneer één logical partition disproportioneel meer requests krijgt dan andere:

```
❌ Slecht voorbeeld: Partition key = "/region"

Partition "europe": 90% van alle requests    ← HOT PARTITION
Partition "asia":    5% van alle requests
Partition "africa":  5% van alle requests

Resultaat: Performance bottleneck, throttling bij 10,000 RU/s limiet
```

---

## 🖥️ Physical Partitions

**Physical partitions** zijn de **daadwerkelijke servers** die logical partitions hosten. Azure beheert deze automatisch.

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Capaciteit** | Max **10,000 RU/s** en **50 GB storage** per physical partition |
| **Management** | Volledig **automatisch** door Azure |
| **Hosting** | Kan **meerdere logical partitions** bevatten |
| **Splitting** | Automatisch gesplitst bij schaalgroei |
| **Merging** | Niet ondersteund (geen automatische merge) |

### 🔄 Automatic Scaling

Azure Cosmos DB splitst automatisch physical partitions wanneer:
- **Storage** de 50 GB nadert
- **Throughput** de 10,000 RU/s nadert

```
Initial state:
Physical Partition 1: [Logical A, Logical B, Logical C]

After split (automatisch):
Physical Partition 1: [Logical A, Logical B]
Physical Partition 2: [Logical C]
```

### 💡 Belangrijk

- Je hebt **geen controle** over physical partitions
- Je **kunt niet mergen** na split
- Logical partitions blijven altijd op **één physical partition**

## 🎯 Partition Key Selectie - Strategieën

Het kiezen van de juiste partition key is **cruciaal** voor goede performance. Hier zijn de belangrijkste strategieën:

### 1️⃣ High Cardinality (Veel Unieke Waarden)

**✅ Doel:** Vermijd hot partitions door data gelijkmatig te verdelen.

```
✅ Goed: /userId (miljoenen unieke gebruikers)
✅ Goed: /orderId (miljoenen unieke orders)
✅ Goed: /deviceId (honderdduizenden IoT devices)

❌ Slecht: /country (slechts ~200 waarden)
❌ Slecht: /isActive (boolean: 2 waarden!)
❌ Slecht: /category (beperkt aantal categorieën)
```

### 2️⃣ Even Distribution (Gelijkmatige Verdeling)

**✅ Doel:** Gelijke hoeveelheid data en requests per partition.

```
❌ Ongelijkmatig:
Partition "VIP-customers":     1000 items, 5000 RU/s
Partition "regular-customers": 50 items,   100 RU/s

✅ Gelijkmatig:
Partition "customer-123": 500 items, 1000 RU/s
Partition "customer-456": 480 items, 950 RU/s
Partition "customer-789": 520 items, 1050 RU/s
```

### 3️⃣ Query Pattern Alignment

**✅ Doel:** Partition key moet voorkomen in WHERE clause van je meest frequente queries.

```sql
-- Query pattern: Zoek orders voor specifieke klant
SELECT * FROM c WHERE c.customerId = 'customer-123'
-- ✅ Partition key: /customerId (query blijft binnen één partition)

-- Query pattern: Zoek producten in categorie
SELECT * FROM c WHERE c.category = 'Electronics'
-- ✅ Partition key: /category

-- ❌ Anti-pattern: Cross-partition queries
-- Partition key: /userId
SELECT * FROM c WHERE c.orderDate > '2024-01-01'
-- Query scant ALLE partitions → duur en langzaam
```

### 4️⃣ Multi-tenant Scenarios

**✅ Doel:** Isolatie en performance per tenant.

```
✅ Ideal: /tenantId
- Data van verschillende tenants op verschillende partitions
- Performance isolatie tussen tenants
- Eenvoudige data extraction per tenant

Container: SaaS Application Data
Partition: "tenant-companyA" → Alle data van Company A
Partition: "tenant-companyB" → Alle data van Company B
```

## 🧬 Synthetic Partition Keys

Wanneer **geen enkele property** voldoende unieke waarden heeft, kun je een **synthetic (kunstmatige) partition key** creëren.

### 1️⃣ Concatenation (Samenvoegen)

Combineer meerdere properties voor meer granulariteit:

```json
// Origineel: Partition key "/region" (te weinig waarden)
{
  "id": "order-123",
  "region": "europe",
  "storeId": "store-456"
}

// ✅ Synthetic key: Concatenate region + storeId
{
  "id": "order-123",
  "region": "europe",
  "storeId": "store-456",
  "partitionKey": "europe-store-456"  // ← Synthetic
}

// Configuratie: Partition key path = /partitionKey
// Resultaat: Veel meer unieke combinaties
```

**Use case:** E-commerce met orders per regio én winkel.

---

### 2️⃣ Random Suffix (Willekeurige Achtervoegsel)

Voeg een random nummer toe voor artificiele spreiding:

```json
// Origineel: Te veel requests naar "premium-users"
{
  "id": "user-123",
  "userType": "premium"
}

// ✅ Synthetic key: userType + random suffix
{
  "id": "user-123",
  "userType": "premium",
  "partitionKey": "premium-users-7"  // suffix 0-9
}

// Configuratie: Partition key path = /partitionKey
// Resultaat: "premium-users" wordt verdeeld over 10 partitions
```

**Use case:** Hot partitions door populaire categorieën.

**⚠️ Trade-off:** Queries over alle premium users vereisen nu 10 partition scans.

---

### 3️⃣ Pre-calculated Hash Suffix

Gebruik een hash voor consistente distributie:

```csharp
// Bereken suffix gebaseerd op userId hash
public string CalculatePartitionKey(string userId, int buckets = 10)
{
    int hash = userId.GetHashCode();
    int suffix = Math.Abs(hash % buckets);
    return $"user-{suffix}";
}

// Gebruik
var user = new User
{
    id = "user-12345",
    userId = "user-12345",
    partitionKey = CalculatePartitionKey("user-12345") // "user-3"
};
```

**Voordeel:** Dezelfde user krijgt altijd dezelfde suffix (predictable).

## 📊 Partition Key Selectie - Decision Tree

```
START: Kies een Partition Key
  │
  ├─❓ Is er een property die vaak voorkomt in WHERE clauses?
  │   └─ Ja → Is deze property high cardinality (veel unieke waarden)?
  │       ├─ Ja → ✅ Gebruik deze property als partition key
  │       └─ Nee ↓
  │
  ├─❓ Zijn er multiple properties die samen uniek zijn?
  │   └─ Ja → ✅ Gebruik concatenation (synthetic key)
  │   └─ Nee ↓
  │
  ├─❓ Is dit een multi-tenant scenario?
  │   └─ Ja → ✅ Gebruik /tenantId
  │   └─ Nee ↓
  │
  ├─❓ Heb je een hot partition probleem?
  │   └─ Ja → ✅ Gebruik random suffix of hash suffix
  │   └─ Nee ↓
  │
  └─ ✅ Default: Gebruik een property met highest cardinality
```

## 💻 Voorbeelden - Partitioning

### Azure CLI

```bash
# Variabelen
account="mycosmosaccount"
database="mydatabase"
container="mycontainer"

# Container met simple partition key
az cosmosdb sql container create \
  --account-name $account \
  --database-name $database \
  --name $container \
  --partition-key-path "/userId" \
  --throughput 400

# Container met nested partition key
az cosmosdb sql container create \
  --account-name $account \
  --database-name $database \
  --name orders \
  --partition-key-path "/customer/customerId" \
  --throughput 1000

# Container met synthetic partition key
az cosmosdb sql container create \
  --account-name $account \
  --database-name $database \
  --name products \
  --partition-key-path "/partitionKey" \
  --throughput 4000
```

### C# (.NET SDK)

```csharp
using Microsoft.Azure.Cosmos;

var cosmosClient = new CosmosClient("<connection-string>");
var database = cosmosClient.GetDatabase("mydatabase");

// ========================================
// 1️⃣ Simple Partition Key
// ========================================

var containerProperties = new ContainerProperties
{
    Id = "users",
    PartitionKeyPath = "/userId"
};

Container container = await database.CreateContainerIfNotExistsAsync(
    containerProperties,
    throughput: 400
);

// Item met partition key
var user = new
{
    id = "user-12345",
    userId = "user-12345", // Partition key property
    name = "John Doe",
    email = "john@example.com"
};

await container.CreateItemAsync(user, new PartitionKey("user-12345"));

// ========================================
// 2️⃣ Nested Partition Key
// ========================================

var orderContainer = new ContainerProperties
{
    Id = "orders",
    PartitionKeyPath = "/customer/customerId" // Nested path
};

await database.CreateContainerIfNotExistsAsync(orderContainer, 1000);

// Item met nested partition key
var order = new
{
    id = "order-001",
    customer = new
    {
        customerId = "cust-123", // Nested partition key
        name = "Jane Doe"
    },
    total = 150.00
};

await container.CreateItemAsync(order, new PartitionKey("cust-123"));

// ========================================
// 3️⃣ Synthetic Partition Key - Concatenation
// ========================================

var productContainer = new ContainerProperties
{
    Id = "products",
    PartitionKeyPath = "/partitionKey" // Synthetic key
};

await database.CreateContainerIfNotExistsAsync(productContainer, 4000);

// Create item met synthetic key
var product = new
{
    id = "prod-001",
    category = "Electronics",
    storeId = "store-42",
    partitionKey = "Electronics-store-42", // Concatenated
    name = "Laptop",
    price = 999.99
};

await container.CreateItemAsync(product, new PartitionKey("Electronics-store-42"));

// ========================================
// 4️⃣ Synthetic Partition Key - Random Suffix
// ========================================

public class UserWithSuffix
{
    public string id { get; set; }
    public string userId { get; set; }
    public string userType { get; set; }
    public string partitionKey { get; set; } // Synthetic with suffix
}

// Helper function
public string GetPartitionKeyWithSuffix(string userType, int buckets = 10)
{
    Random random = new Random();
    int suffix = random.Next(0, buckets);
    return $"{userType}-{suffix}";
}

var premiumUser = new UserWithSuffix
{
    id = "user-789",
    userId = "user-789",
    userType = "premium",
    partitionKey = GetPartitionKeyWithSuffix("premium", 10) // "premium-7"
};

await container.CreateItemAsync(premiumUser, new PartitionKey(premiumUser.partitionKey));

// ========================================
// 5️⃣ Synthetic Partition Key - Hash Suffix
// ========================================

public string GetHashBasedPartitionKey(string userId, int buckets = 10)
{
    int hash = userId.GetHashCode();
    int suffix = Math.Abs(hash % buckets);
    return $"user-{suffix}";
}

var userWithHash = new
{
    id = "user-999",
    userId = "user-999",
    partitionKey = GetHashBasedPartitionKey("user-999", 10) // Consistent: "user-3"
};

await container.CreateItemAsync(userWithHash, new PartitionKey(userWithHash.partitionKey));

// ========================================
// 6️⃣ Querying met Partition Key
// ========================================

// ✅ Single-partition query (goedkoopst)
var query = new QueryDefinition(
    "SELECT * FROM c WHERE c.userId = @userId"
).WithParameter("@userId", "user-12345");

FeedIterator<User> iterator = container.GetItemQueryIterator<User>(
    queryDefinition: query,
    requestOptions: new QueryRequestOptions
    {
        PartitionKey = new PartitionKey("user-12345") // Blijft binnen één partition
    }
);

// ❌ Cross-partition query (duur)
var crossPartitionQuery = new QueryDefinition(
    "SELECT * FROM c WHERE c.age > 25"
);

FeedIterator<User> crossIterator = container.GetItemQueryIterator<User>(
    queryDefinition: crossPartitionQuery
    // Geen PartitionKey → scant ALLE partitions
);

// Monitor RU charges
while (crossIterator.HasMoreResults)
{
    FeedResponse<User> response = await crossIterator.ReadNextAsync();
    Console.WriteLine($"RU charge: {response.RequestCharge}"); // Vaak veel hoger
}

// ========================================
// 7️⃣ Point Read (meest efficiënt)
// ========================================

// Met id + partition key = Direct read (1 RU voor 1KB item)
ItemResponse<User> pointRead = await container.ReadItemAsync<User>(
    id: "user-12345",
    partitionKey: new PartitionKey("user-12345")
);
Console.WriteLine($"Point read RU: {pointRead.RequestCharge}"); // ~1 RU

// ❌ Zonder partition key = Cross-partition query (veel duurder)
var query = new QueryDefinition("SELECT * FROM c WHERE c.id = @id")
    .WithParameter("@id", "user-12345");

FeedIterator<User> queryIterator = container.GetItemQueryIterator<User>(query);
// RU charge kan 10x-100x hoger zijn dan point read!
```

## 📊 Partition Key Anti-Patterns

### ❌ 1. Timestamp als Partition Key

```json
{
  "id": "order-123",
  "orderDate": "2024-11-07", // Partition key
  "customerId": "cust-456"
}
```

**Probleem:**
- Alle nieuwe orders gaan naar **dezelfde partition** (vandaag)
- Oude partitions worden nooit meer gebruikt (write hot spot)
- Queries over recente data zijn allemaal in één partition (read hot spot)

**✅ Beter:** Gebruik customerId of orderId.

---

### ❌ 2. Boolean als Partition Key

```json
{
  "id": "user-123",
  "isActive": true // Partition key (2 waarden!)
}
```

**Probleem:**
- Slechts **2 partitions** (true/false)
- Geen schaling mogelijk
- Zeer ongelijkmatige verdeling als 90% users active zijn

**✅ Beter:** Gebruik userId.

---

### ❌ 3. Static Value als Partition Key

```json
{
  "id": "product-123",
  "type": "product" // Partition key (1 waarde!)
}
```

**Probleem:**
- **Alle data in één partition**
- Max 20 GB storage limiet
- Max 10,000 RU/s throughput limiet
- Geen horizontale schaling

**✅ Beter:** Gebruik productId of category.

---

### ❌ 4. Enum met Weinig Waarden

```json
{
  "id": "order-123",
  "status": "pending" // Partition key: pending/processing/completed/cancelled
}
```

**Probleem:**
- Slechts 4 partitions
- "Processing" orders kunnen hot partition worden
- Beperkte schaalbaarheid

**✅ Beter:** Gebruik orderId of customerId.

## 🎯 Validation Checklist

Voordat je een partition key kiest, controleer het volgende:

| ✅ Criterium | Vraag |
|--------------|-------|
| **High cardinality** | Heeft de property duizenden of meer unieke waarden? |
| **Even distribution** | Worden requests en data gelijk verdeeld over waarden? |
| **Query alignment** | Komt de property voor in WHERE clauses van frequente queries? |
| **Future growth** | Blijft de property high cardinality bij schaling? |
| **Immutability** | Verandert de waarde nooit (data migratie is duur)? |
| **Size limit** | Is één logical partition altijd < 20 GB? |
| **Throughput** | Heeft één logical partition nooit > 10,000 RU/s nodig? |

## 🏆 Best Practices

### ✅ Do's

| Praktijk | Reden |
|----------|-------|
| **Kies high cardinality properties** | Vermijdt hot partitions en schaalt beter |
| **Test met production-like data** | Valideer verdeling en query patterns |
| **Monitor partition metrics** | Check voor ongelijke verdeling in Azure Portal |
| **Document partition key rationale** | Leg uit waarom je deze key hebt gekozen |
| **Use point reads wanneer mogelijk** | id + partition key = 1 RU (goedkoopst) |
| **Gebruik synthetic keys bij noodzaak** | Concatenation of hash suffix als geen goede property bestaat |

### ❌ Don'ts

| Anti-pattern | Waarom niet? |
|--------------|---------------|
| **Timestamp/date als partition key** | Creëert hot spot voor recente data |
| **Boolean of enum als partition key** | Te weinig unieke waarden |
| **Partition key achteraf wijzigen** | Niet mogelijk - vereist volledige data migratie |
| **Negeren van 20 GB limiet** | Logical partition kan niet groeien boven 20 GB |
| **Elke query cross-partition maken** | Zeer duur en langzaam |
| **Random GUID per item** | Voorkomt batch operations en related data queries |

## 📈 Monitoring & Troubleshooting

### Azure Portal Metrics

Monitor de volgende metrics voor partition health:

| Metric | Wat te checken |
|--------|----------------|
| **Partition Key RU Consumption** | Zijn sommige partitions disproportioneel hoog? |
| **Storage Distribution** | Zijn sommige logical partitions dicht bij 20 GB? |
| **Request Rate by Partition** | Krijgen sommige partitions veel meer requests? |
| **Throttled Requests (429)** | Duidt op hot partition die 10,000 RU/s limiet raakt |

### Troubleshooting Hot Partitions

```csharp
// Query om partition distributie te analyseren
var query = new QueryDefinition(@"
    SELECT c.partitionKeyProperty, COUNT(1) as itemCount
    FROM c
    GROUP BY c.partitionKeyProperty
");

// Check welke partitions de meeste items hebben
// Als één partition veel meer heeft → hot partition
```

**Oplossingen:**
1. **Re-design partition key** (nieuwe container + data migratie)
2. **Synthetic key toevoegen** (random/hash suffix)
3. **Increase throughput** (korte termijn oplossing, niet ideaal)
