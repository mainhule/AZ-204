# 🎚️ Azure Cosmos DB - Consistency Levels

## 📖 Wat zijn Consistency Levels?

In **gedistribueerde databases** die data over meerdere regio's repliceren, is er altijd een **trade-off** tussen:
- **📊 Consistency** - Hoe "vers" is de data die je leest?
- **⚡ Performance** - Hoe snel krijg je een response?
- **✅ Availability** - Hoe betrouwbaar is de service bij uitval?

Azure Cosmos DB biedt **5 consistency levels** waarmee je deze trade-off kunt fine-tunen op basis van je applicatie requirements.

---

## 🌟 Consistency Spectrum

Van **sterkste consistency** (langzaamst) naar **zwakste consistency** (snelst):

```
Strong → Bounded Staleness → Session → Consistent Prefix → Eventual

🔒 Sterke Garanties     🏷️ Balanced          ⚡ Beste Performance
📉 Lagere Availability  ⚖️ Goede Trade-off   📈 Hoogste Availability
⏱️ Hogere Latency       ⏱️ Moderate Latency  ⚡ Laagste Latency
```

![Consistency Spectrum](https://learn.microsoft.com/en-us/training/wwl-azure/explore-azure-cosmos-db/media/five-consistency-levels.png)

## 🔐 1. Strong Consistency

**💡 Eenvoudig gezegd:**  
Elke lezer ziet **altijd** de meest recente versie van de data. Geen enkele client zal ooit "oude" data zien.

### ⚙️ Hoe het werkt

- **Synchronous replication:** Writes worden bevestigd **pas nadat** ze zijn gerepliceerd naar een quorum van replica's
- **Linearizability:** Operaties lijken te gebeuren in één enkele, globale volgorde
- **No stale reads:** Clients zien nooit partial writes of oude versies

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Garantie** | Lezen geeft **altijd** de laatste committed write |
| **Latency** | ⏱️ **Hoogste** (wacht op replicatie naar meerdere regio's) |
| **Availability** | 📉 **Laagste** (kan niet lezen/schrijven bij regio uitval) |
| **Read consistency** | 100% - Altijd de laatste versie |
| **Multi-region** | ❌ Niet ondersteund voor multi-region write accounts |

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **Financial transactions** - Banktransacties, betalingen
- **Inventory management** - Stock levels moeten exact zijn
- **Booking systems** - Voorkomen van double-bookings
- **Audit logs** - Compliance-kritische data

❌ **Wanneer niet te gebruiken:**
- Global applications met lage latency requirements
- High-availability scenarios met regio failover
- Multi-region write scenarios

### 💻 Voorbeeld Scenario

```
Gebruiker A: Schrijft saldo = €100
Gebruiker B: Leest saldo direct daarna
Resultaat: Gebruiker B ziet ALTIJD €100 (nooit oude waarde)
```

## ⏳ 2. Bounded Staleness

**💡 Eenvoudig gezegd:**  
Data kan **enigszins verouderd** zijn, maar je weet **precies hoeveel** (bepaald door K operaties of T tijd).

### ⚙️ Hoe het werkt

- Je stelt een **"staleness window"** in via:
  - **K** = Aantal write operaties (versies)
  - **T** = Tijdsinterval (seconden)
- Reads kunnen **maximaal K versies** of **T seconden** achter lopen
- Binnen één regio gedraagt het zich als **Strong**

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Garantie** | Maximale staleness van **K operaties** of **T seconden** |
| **Latency** | ⏱️ **Matig** (lager dan Strong) |
| **Availability** | 📊 **Matig** (beter dan Strong) |
| **Read consistency** | Bounded - Binnen gedefinieerde window |
| **Multi-region** | ✅ Ondersteund voor multi-region write |

### ⚙️ Configuratie Limieten

| Account Type | Minimum K | Minimum T |
|-------------|-----------|-----------|
| **Single-region** | 10 write operaties | 5 seconden |
| **Multi-region** | 100,000 write operaties | 300 seconden (5 minuten) |

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **Game leaderboards** - Kleine vertraging in scores is acceptabel
- **Social media feeds** - Recent posts hoeven niet exact real-time
- **Monitoring dashboards** - Metrics mogen enkele seconden oud zijn
- **Multi-region applications** met predictable staleness requirements

❌ **Wanneer niet te gebruiken:**
- Real-time trading platforms
- Critical health monitoring systems

### 💻 Voorbeeld Scenario

```
Configuratie: K = 10 versies, T = 5 seconden

Schrijf operaties:
10:00:00 - Versie 1
10:00:01 - Versie 2
10:00:02 - Versie 3
...
10:00:10 - Versie 11

Lezer in regio B (10:00:11):
- Mag minimaal versie 1 zien (11 - 10 = versie 1)
- Of versies vanaf 10:00:06 (5 seconden geleden)
```

## 👤 3. Session Consistency (⏺️ Default)

**💡 Eenvoudig gezegd:**  
Binnen **één gebruikerssessie** zie je altijd je **eigen writes** en data in de juiste volgorde. Andere gebruikers kunnen oudere data zien.

### ⚙️ Hoe het werkt

- Elke client krijgt een **session token** bij writes
- Met deze token zie je **altijd je eigen writes** (read-your-writes)
- **Monotonic reads:** Data wordt nooit "ouder" binnen je sessie
- **Andere sessies** kunnen oudere versies zien

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Garantie** | Read-your-writes, monotonic reads binnen sessie |
| **Latency** | ⚡ **Laag** (geen cross-region synchronisatie) |
| **Availability** | 📈 **Hoog** |
| **Read consistency** | Per sessie consistent |
| **Multi-region** | ✅ Ondersteund, session token zorgt voor consistency |

### 🔑 Session Token

```csharp
// Session token wordt automatisch beheerd door SDK
ItemResponse<User> writeResponse = await container.CreateItemAsync(user);
string sessionToken = writeResponse.Headers.Session;

// Bij volgende read wordt session token automatisch gebruikt
ItemResponse<User> readResponse = await container.ReadItemAsync<User>(id, partitionKey);
// ☑️ Ziet gegarandeerd de zojuist geschreven data
```

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **E-commerce shopping carts** - Gebruiker ziet eigen toegevoegde items
- **Social media posts** - Auteur ziet direct eigen post
- **User profile updates** - Gebruiker ziet eigen wijzigingen direct
- **Document editing** - Schrijver ziet eigen edits
- **95% van alle applicaties** - Best balance tussen consistency en performance

❌ **Wanneer niet te gebruiken:**
- Scenario's waar **alle gebruikers** dezelfde versie moeten zien
- Cross-device scenarios zonder session management

### 💻 Voorbeeld Scenario

```
Gebruiker A (Sessie 1):
1. Voegt product X toe aan cart
2. Refresh pagina
3. ✅ Ziet product X (read-your-writes)

Gebruiker B (Sessie 2):
1. Bekijkt dezelfde cart container
2. ❓ Kan oudere versie zien (zonder product X van gebruiker A)
```

## 📜 4. Consistent Prefix

**💡 Eenvoudig gezegd:**  
Je ziet updates **altijd in de juiste volgorde**, maar mogelijk niet de allerlaatste versie. Geen "gaps" in de volgorde.

### ⚙️ Hoe het werkt

- **In-order reads:** Als write A gebeurde vóór write B, zie je nooit B zonder A
- Geen garantie dat je de **laatste** versie ziet
- Wel garantie dat je **geen tussenliggende versies mist**

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Garantie** | Reads respecteren write volgorde (geen gaps) |
| **Latency** | ⚡ **Zeer laag** |
| **Availability** | 📈 **Zeer hoog** |
| **Read consistency** | Sequentiële consistentie |
| **Multi-region** | ✅ Excellent voor globally distributed reads |

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **Event logs** - Volgorde van events is belangrijk
- **Message feeds** - Posts moeten in chronologische volgorde
- **Status updates** - State transitions moeten logisch zijn
- **Activity streams** - Activiteiten in juiste volgorde

❌ **Wanneer niet te gebruiken:**
- Scenario's waar je **altijd** de laatste versie moet zien
- Scenarios zonder natuurlijke ordering

### 💻 Voorbeeld Scenario

```
Writes in volgorde:
1. Status = "Created"
2. Status = "InProgress"  
3. Status = "Completed"

Lezer met Consistent Prefix:
✅ Mogelijk: Ziet "Created"
✅ Mogelijk: Ziet "Created" → "InProgress"
✅ Mogelijk: Ziet "Created" → "InProgress" → "Completed"
❌ ONMOGELIJK: Ziet "InProgress" zonder "Created" gezien te hebben
❌ ONMOGELIJK: Ziet "Completed" zonder "Created" en "InProgress"
```

## ⚡ 5. Eventual Consistency

**💡 Eenvoudig gezegd:**  
**Ultieme performance en availability**, maar je kunt **tijdelijk oude data** zien en mogelijk **out-of-order** reads.

### ⚙️ Hoe het werkt

- **Asynchronous replication:** Writes worden direct bevestigd
- Geen garanties over **volgorde** of **recentheid**
- **Uiteindelijk** (eventually) worden alle replica's consistent
- **Weakest** maar **fastest** model

### 📊 Karakteristieken

| Aspect | Details |
|--------|---------|
| **Garantie** | Uiteindelijk consistent (geen directe garanties) |
| **Latency** | ⚡ **Absolute laagste** |
| **Availability** | 📈 **Absolute hoogste** |
| **Read consistency** | Geen garanties |
| **Multi-region** | ✅ Beste keuze voor global write-heavy workloads |

### 🎯 Use Cases

✅ **Wanneer te gebruiken:**
- **Social media likes/views** - Exacte count is niet kritiek
- **Analytics/telemetry** - Approximate counts zijn voldoende
- **Product reviews** - Volgorde niet kritiek
- **User-generated content** - Feed ordering niet strikt nodig
- **High-throughput logging** - Volume belangrijker dan volgorde

❌ **Wanneer niet te gebruiken:**
- Financial transactions
- Inventory management
- Booking systems
- Scenario's waar volgorde cruciaal is

### 💻 Voorbeeld Scenario

```
Writes:
1. Tweet: "Hello" (versie 1)
2. Tweet: "World" (versie 2)

Lezer A: Ziet versie 2 direct (recent)
Lezer B: Ziet versie 1 (oude data)
Lezer C: Ziet versie 2, dan versie 1 (out-of-order!)

Na enkele seconden: Alle lezers zien versie 2
```

## 📊 Vergelijking Matrix

| Consistency Level | Latency | Availability | Read Garanties | Use Case |
|-------------------|---------|-------------|----------------|----------|
| **Strong** 🔒 | Hoogste | Laagste | Altijd laatste versie | Banking, inventory |
| **Bounded Staleness** ⏳ | Hoog | Matig | Max K versies / T tijd oud | Leaderboards, monitoring |
| **Session** 👤⏺️ | Laag | Hoog | Read-your-writes per sessie | E-commerce, profiles |
| **Consistent Prefix** 📜 | Zeer laag | Zeer hoog | In-order, mogelijk niet recent | Event logs, feeds |
| **Eventual** ⚡ | Laagste | Hoogste | Geen garanties | Likes, analytics |

## 💻 Configuratie Voorbeelden

### Azure CLI

```bash
# Account consistency level ophalen
az cosmosdb show \
  --name mycosmosaccount \
  --resource-group myResourceGroup \
  --query defaultConsistencyLevel

# Account consistency level instellen
az cosmosdb update \
  --name mycosmosaccount \
  --resource-group myResourceGroup \
  --default-consistency-level "Session"

# Bounded Staleness met specifieke waarden
az cosmosdb update \
  --name mycosmosaccount \
  --resource-group myResourceGroup \
  --default-consistency-level "BoundedStaleness" \
  --max-staleness-prefix 100 \
  --max-interval 300
```

---

### C# (.NET SDK)

```csharp
// ========================================
// Account-level consistency
// ========================================

var cosmosClient = new CosmosClient(
    accountEndpoint: "https://myaccount.documents.azure.com:443/",
    authKeyOrResourceToken: "<key>"
);

// Huidige default consistency level ophalen
ConsistencyLevel accountLevel = cosmosClient.ClientOptions.ConsistencyLevel ?? ConsistencyLevel.Session;
Console.WriteLine($"Account consistency: {accountLevel}");

// ========================================
// Request-level consistency override
// ========================================

// Je kunt een ZWAKKERE consistency gebruiken per request
// (maar NOOIT sterker dan account-level setting)

var container = cosmosClient.GetContainer("database", "container");

// Voorbeeld: Account heeft Session, maar we willen Eventual voor deze query
var query = new QueryDefinition("SELECT * FROM c");

FeedIterator<dynamic> iterator = container.GetItemQueryIterator<dynamic>(
    queryDefinition: query,
    requestOptions: new QueryRequestOptions
    {
        ConsistencyLevel = ConsistencyLevel.Eventual // Override naar zwakkere level
    }
);

while (iterator.HasMoreResults)
{
    FeedResponse<dynamic> response = await iterator.ReadNextAsync();
    Console.WriteLine($"RU charge: {response.RequestCharge}");
    // Eventual consistency kan lagere RU kosten hebben
}

// Point read met specifieke consistency
ItemResponse<User> response = await container.ReadItemAsync<User>(
    id: "1",
    partitionKey: new PartitionKey("user123"),
    requestOptions: new ItemRequestOptions
    {
        ConsistencyLevel = ConsistencyLevel.Eventual
    }
);

// ========================================
// Session token manual management
// ========================================

// Session consistency gebruikt automatisch session tokens,
// maar je kunt ze ook handmatig beheren voor cross-client scenarios

// Write operation
ItemResponse<User> writeResponse = await container.CreateItemAsync(user);
string sessionToken = writeResponse.Headers.Session;

// Sla session token op (bijv. in user session, cache, etc.)
// httpContext.Session.SetString("CosmosSessionToken", sessionToken);

// Later: Read met specifieke session token
ItemResponse<User> readResponse = await container.ReadItemAsync<User>(
    id: "1",
    partitionKey: new PartitionKey("user123"),
    requestOptions: new ItemRequestOptions
    {
        SessionToken = sessionToken // Forceer consistency binnen deze sessie
    }
);

// ========================================
// Bounded Staleness configuratie check
// ========================================

// Dit is een account-level setting, niet beschikbaar via SDK
// Moet via Azure Portal of CLI worden geconfigureerd:
// - maxStalenessPrefix: 10-100000 (K operaties)
// - maxIntervalInSeconds: 5-86400 (T seconden)
```

## 🎯 Beslisboom: Welke Consistency Level?

```
START
  │
  ├─❓ Moet ELKE lezer de ABSOLUTE laatste data zien?
  │   └─ Ja → Strong 🔒
  │   └─ Nee ↓
  │
  ├─❓ Weet je hoeveel "achterstand" acceptabel is?
  │   └─ Ja (bijv. max 10 versies, max 5 sec) → Bounded Staleness ⏳
  │   └─ Nee ↓
  │
  ├─❓ Is het genoeg dat een gebruiker zijn EIGEN writes ziet?
  │   └─ Ja → Session 👤 (⏺️ AANBEVOLEN)
  │   └─ Nee ↓
  │
  ├─❓ Is VOLGORDE van events belangrijk?
  │   └─ Ja → Consistent Prefix 📜
  │   └─ Nee ↓
  │
  └─ Eventual ⚡ (Beste performance)
```

## 📌 Belangrijke Details

### 🌍 Multi-region Behavior

| Consistency Level | Single-region Writes | Multi-region Writes |
|-------------------|---------------------|---------------------|
| Strong | ✅ Ondersteund | ❌ Niet ondersteund |
| Bounded Staleness | ✅ | ✅ |
| Session | ✅ | ✅ (via session tokens) |
| Consistent Prefix | ✅ | ✅ |
| Eventual | ✅ | ✅ |

### 💰 Cost Impact

- **Stronger consistency** = **Hogere RU kosten** (meer replicatie overhead)
- **Weaker consistency** = **Lagere RU kosten** (minder replicatie overhead)
- **Session** biedt beste balance voor de meeste scenarios

### ⚠️ Consistency Overrides

```
Account level: Strong
    │
    └─ Request level: Session ❌ NIET MOGELIJK (sterker dan account)
    
Account level: Session
    │
    └─ Request level: Eventual ✅ TOEGESTAAN (zwakker dan account)
```

Je kunt **per request alleen een ZWAKKERE consistency** instellen dan de account default.

## 🏆 Best Practices

### ✅ Do's

| Praktijk | Reden |
|----------|-------|
| **Start met Session** | Beste default voor 95% van applicaties |
| **Test verschillende levels** | Meet latency en RU costs voor je workload |
| **Gebruik Eventual voor analytics** | Analytics queries hoeven niet real-time |
| **Monitor consistency metrics** | Check staleness metrics in Azure Monitor |
| **Document je keuze** | Leg uit waarom je een specifieke level hebt gekozen |

### ❌ Don'ts

| Anti-pattern | Waarom niet? |
|--------------|---------------|
| **Strong voor alle scenarios** | Onnodig duur en langzaam |
| **Eventual voor financial data** | Risico op incorrecte transacties |
| **Negeren van multi-region impact** | Strong werkt niet met multi-region writes |
| **Per-request overrides overal gebruiken** | Complexiteit en moeilijk te debuggen |
| **Consistency level wijzigen zonder testing** | Kan applicatie gedrag fundamenteel veranderen |
