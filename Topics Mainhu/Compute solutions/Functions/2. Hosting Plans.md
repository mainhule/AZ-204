# Hosting Plans

Consumption is het laagste plan dat scaling ondersteunt en event-based scheduling gedrag biedt.

## Hosting Plans Vergelijking

### 💰 Consumption Plan
**Cost Model:** Serverless (betaal per gebruik)

**Cold Start:** Wanneer idle of geschaald naar nul instances

**Scaling:** Event-driven

**Best voor:**
- Low-traffic, kostenbewuste workloads
- Variabele of onvoorspelbare workloads

**Beperkingen:**
- ❌ Geen container support
- ❌ 5-10 min timeout
- ❌ Max instances: 100 (Linux), 200 (Windows)
- ❌ Geen VNET integration
- ❌ Geen support voor durable functions chaining large executions

---

### ⚡ Flex Consumption Plan
**Cost Model:** Serverless (betaal per gebruik) + geheugen voor always-ready instances

**Cold Start:** Vermindert cold starts tijdens scaling via always-ready instances

**Scaling:** Per-function

**Best voor:**
- Low-latency apps die snellere startup nodig hebben

**Beperkingen:**
- ❌ Geen containers of Windows support
- ❌ Regionale beschikbaarheid beperkt

---

### 💎 Premium Plan
**Cost Model:** Voorspelbaar: runtime + geheugen voor pre-warmed instances

**Cold Start:** Geen cold starts (minimum instance count altijd warm)

**Scaling:** Event-driven

**Best voor:**
- Productie-grade apps
- Langlopende taken
- Custom images

**Beperkingen:**
- ⚠️ Moet minimaal één instance warm houden
- ⚠️ Hogere kosten

---

### 🏢 Dedicated Plan
**Cost Model:** Voorspelbaar (vast) - App Service Plan pricing

**Cold Start:** Vermeden voor always-on instance, maar kan voorkomen tijdens scale-out (geen pre-warmed instances)

**Scaling:** Manual of App Service autoscale (rule-based)

**Best voor:**
- App Service integratie (hergebruik VMs)
- Meerdere apps op één plan draaien
- Toegang tot grotere compute sizes
- Volledige isolatie (VNET) & secure networking (ASE)

**Beperkingen:**
- ⚠️ Niet kosteneffectief tenzij volledig benut
- ⚠️ Manual scaling tenzij App Service autoscale gebruikt wordt

---

### 🐳 Container Apps Plan
**Cost Model:** Azure Container Apps plan (consumption / dedicated)

**Cold Start:** Hangt af van `minReplicas`: 1+ vermijdt cold start

**Scaling:** Event-driven (KEDA based)

**Best voor:**
- Custom runtimes/libraries
- Legacy/on-prem naar containers
- Geen Kubernetes management
- GPU-powered functions

**Beperkingen:**
- ⚠️ Cold start tenzij minReplica ≥ 1
- ⚠️ Complexere setup

---

## Scaling Types

### 🎯 Event-driven
De **scale controller** past resources aan op basis van event rates en trigger types. Het gebruikt heuristics voor elk trigger type (bijvoorbeeld: voor Queue storage trigger schaalt het op basis van queue lengte en leeftijd van oudste queue message).

### 📊 Per function
De meeste functies schalen onafhankelijk, terwijl HTTP, Blob (Event Grid), en Durable Function triggers elk schalen als gegroepeerde sets op gedeelde instances.

### 📈 Rule-based (autoscale)
In tegenstelling tot event-driven scaling, reageert het niet direct op function invocations, maar op resource metrics (CPU, geheugen, HTTP queue length) of schema's.

## CLI Commando's

```bash
# Function app plan maken
az functionapp plan create \
    --name MyPlan \
    --resource-group MyResourceGroup \
    --sku F1 # F1(Free), D1(Shared), B1(Basic Small), S1(Standard Small), P1V2(Premium V2 Small), I1(Isolated Small), K1(Kubernetes) \
    --is-linux true \
    --location eastus \
    --min-instances 1 \
    --max-burst 10 \
    --zone-redundant # Minimum instance count is 3

# Alle Consumption plans in resource group ophalen
az functionapp plan list --resource-group MyResourceGroup --query "[?sku.family=='Y'].{PlanName:name,Sites:numberOfSites}" -o table

# Hosting plan type ophalen
appServicePlanId=$(az functionapp show --name MyFunctionApp --resource-group MyResourceGroup --query appServicePlanId --output tsv)
az appservice plan list --query "[?id=='$appServicePlanId'].sku.tier" --output tsv

# Alle Premium plans in resource group ophalen
az functionapp plan list --resource-group MyResourceGroup --query "[?sku.family=='EP'].{PlanName:name,Sites:numberOfSites}" -o table
```
